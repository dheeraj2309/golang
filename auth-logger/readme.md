## Middleware Auth and Logging
This project aims to understand the design of middleware , how they are used , the use of `context` package of go.
At its core, middleware is software that acts as a bridge between an incoming request and your core business logic
#### Learnings :
* **Interfaces and Contracts**: You will learn how Go uses interfaces to enforce structure, specifically how anything implementing a `ServeHTTP` method can be treated as a web server.
* **Higher-Order Functions**: You will practice writing closures—functions that return other functions—which is the backbone of Go middleware.
* **The Context Package**: You will master context.Context, which is crucial not just for passing data (like Auth tokens), but also for handling request timeouts and cancellations in Go.
* **Struct Embedding**: To make the Logger work, you will learn how to embed Go's default response writer inside your own custom struct so you can "spy" on the status codes being sent back to the client.

There is one major architectural question left: If the middleware verifies the token and extracts the Username, how does it pass that Username down to the final handler?In Node.js, you would just mutate the request object: `req.user = username`.Go is strictly typed and does not allow you to mutate the standard HTTP request struct on the fly.
To solve this, Go uses a package called `context`.
* The middleware takes the incoming request's context.
* It creates a clone of that context, attaching the newly verified Username to it as a key-value pair.
* It creates a clone of the HTTP request, injecting this new context into it.
* It passes this cloned request down to the next handler.

When the final handler runs, it simply extracts the Username from its context, knowing with 100% certainty that the middleware put it there.

## `http.Handler` and `http.HandlerFunc()` confusion?
> `http.Handler` is an interface <br>

```go
type Handler interface {
    ServeHTTP(ResponseWriter, *Request)
}
```

`http.Handler` is not a function. It is a contract. It says: "I don't care if you are a struct, a string, a router, or a function. As long as you have a method named `ServeHTTP`, you are an `http.Handler`."

> `http.HandlerFunc()` is an ADAPTER

```go
type HandlerFunc func(ResponseWriter, *Request)
```
`http.HandlerFunc` is a specific data type. It is a brilliant Go hack. It takes a normal, boring function and attaches a `ServeHTTP` method to it. By doing this, it converts a standard function into an `http.Handler` interface.


* Your function signature promises to return an `http.Handler` (the interface).
But inside your middleware, you are writing an anonymous function: `func(w http.ResponseWriter, r *http.Request) { ... }`
* A raw anonymous function does not implement the `http.Handler` interface. The compiler will reject it.
So, you wrap your anonymous function in `http.HandlerFunc()`. 
*This acts as a type cast. It tells Go: "Take this anonymous function, slap a `ServeHTTP` method onto it, and return it so it satisfies the `http.Handler` interface I promised."
